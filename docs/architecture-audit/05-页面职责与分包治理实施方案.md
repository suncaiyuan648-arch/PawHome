## 1. 治理决策

按**业务对象、用户任务和写入权限**划分页面职责，按**实际构建依赖和资源体积**划分物理分包。入口来自“我的”、背景颜色相同、Figma 画板名字相近，都不能决定页面归属。

本轮建议明确执行以下决策：

1. 动态、救助、领养、小院、投喂分别归自己的业务域；个人中心只聚合入口和个人资料，不再装下所有“我的某业务”。
2. 将动物档案从领养域提取为 `animal`：动物在领养前后持续存在，也参与小院、相册、云养、投喂、救助。`petDetail` 不应天然归属领养。
3. 救助申请、申请成功、申请者进度、公开详情、证实和救助评审使用明确的救助路由；领养申请、进度、院主审核、领养评审使用领养路由。
4. 将审核列表与审核详情分开；将申请者进度与审核者操作分开。救助审核与领养审核不再由一个页面靠 `type` 更换业务处理器。
5. 保留合理聚合：评审团任务大厅可以展示不同业务的任务卡；消息中心、搜索、个人中心也是聚合入口。它们只负责查询摘要和分发，不承担各业务的审批提交。
6. 同一订单的不同角色视角、同一列表的筛选、同一实体的空态/加载态、同一表单的猫狗差异，继续用明确状态或组件变体。**一个 Figma Frame 不等于一个页面。**
7. 主包最终保留现有四个 Tab 页面和必要基础设施，消息分类列表移入分包；主包治理完成门槛为 **≤1536KiB（1.5MiB）**，平台单包硬上限按 **2048KiB（2MiB）** 执行。
8. 先修构建/路由门禁和依赖归属，再迁页面；旧路由保留轻量兼容壳，不能通过旧壳静态引入新分包页面。生产代码不再使用 `frame=44`、`variant=90` 等画板编号驱动业务。

这里将“页”定义为有独立导航地址、对象上下文和生命周期的路由入口；“视图”是页内状态/内容；“组件”是无页面所有权的复用单元；“分包”是下载和引用边界。四者不要混为一谈。

## 3. 六条业务主链路与页面边界

### 3.1 页面拆分规则

以下任一条件成立，优先拆成独立路由：写入不同业务记录、操作权限不同、主要加载对象不同、独立分享/恢复要求不同，或列表与单条详情具有不同返回语义。

以下情况默认留在同页：同一对象的生命周期状态、同一列表筛选、加载/空/错误状态、弹层开关、只读/可操作的同一订单视图、猫狗这类稳定表单变体。遇到实质不同的工作台职责，再从该规则升级拆页。

| 类型 | 应负责 | 不应负责 |
|---|---|---|
| 聚合入口 | 加载摘要、计数、切换业务入口、路由分发 | 内嵌完整救助/领养申请表或审批处理器 |
| 列表 | 筛选、分页、定位记录、恢复滚动 | 在同一 URL 切换到另一条记录详情 |
| 详情 | 单个实体读取、允许的查看行为 | 用缺失 ID 回退另一条 demo |
| 业务工作流 | 本域表单/进度/审核、状态约束 | 由主题色、frame 或 role 字符串决定写哪种记录 |
| 结果 | 展示已完成操作的结果、返回/下一步 | onLoad 再次提交、重复创建订单 |
| 选择器 | 明确输入/输出、取消、回填 | 承担调用方业务提交、传任意 returnUrl 执行跳转 |

### 3.2 动态

链路：**首页动态流 → 动态详情 → 评论/回复/关联小院或动物；发布入口 → 编辑动态 → 选择关联投喂订单 → 发布结果 → 动态详情。**

- 首页是主包聚合入口；动态详情、编辑器、发布结果归 `dynamic`。
- `postFeed` 改为 `dynamic/editor`，文案使用“发布动态”，避免把动态发布误解为创建投喂订单。
- 选择订单默认是编辑器中的 `PawOrderSelectSheet`，不增加一个只显示 sheet 的正式页面。
- 投喂反馈可复用动态编辑器，但输入为 `scene=feeding-feedback&orderId=...`。场景只影响本域动态内容及关联关系，不执行投喂支付。
- 评论空态、语音/表情/回复弹层仍为动态详情状态；发布成功页与投喂成功页分开归属。

### 3.3 救助

链路：**发布入口 → 救助申请 → 申请结果 → 我的救助进度；基金列表 → 救助详情 → 证实列表 → 证实表单；评审任务大厅 → 救助评审详情。**

- `rescue/apply` 只创建救助申请，持有 `rescueId`；不包含 adoption 提交分支。
- `rescue/progress` 是申请者视角；当前既有能力是显示平台审核状态和材料，不加审核按钮。
- `rescue/fund` 保持基金池统计与申请公开列表，不改造成平台打款后台。
- `rescue/detail` 展示公开材料、证实和合法的公开交互；有资格投票时进入 `rescue/review/detail`。迁移现有投票行为要保持相同记录和用户体验，不能让两处各自记录票数。
- `rescue/proof/list`、`rescue/proof/create` 明确属于救助；领养确认上传不叫“救助证实”。
- 平台审核、打款操作作为服务边界，不在本轮凭空增加小程序管理端。救助申请的 `applicationStatus` 与基金/投票/打款状态分别建模，不强制塞进一个枚举。

### 3.4 领养

链路：**动物详情 → 选择动物 → 领养申请 → 申请结果 → 我的领养 → 进度；审核列表 → 审核详情 → 申请者上传确认材料 → 院主确认 → 领养评审 → 确认成功 → 奖励地址/订单。**

- 列表、申请、申请者进度、审核列表、审核详情、确认材料、奖励领取各有稳定职责。
- 云家长审核和院主审核仍是领养审核详情的能力/阶段，角色与单据关系决定允许动作；无需按每个同意/拒绝状态造新路由。
- 申请内容与领养信息（包括小院位置、联系方式）属于同一领养单的只读子视图，可用 `view=application|adoption-info`，不再暴露 `frame=48/49`。审核详情自身的小院信息可用 `view=yard`，两者按页面合同区分。
- 保持已有流程：可选云家长审核 → 院主审核 → 上传材料 → 院主确认 → 评审团确认 → 领养成功 → 奖励。失败记录 `failureStage`；当前禁用重新开启的约束继续保留。
- 申请成功是 `adoption/result` 的 `outcome=application-submitted`；审核结果、确认材料提交结果等同域结果可共用语义化 `outcome`，不需要再保留两个重复的成功页。
- `extras` 拆为“助力领养”“领养额度”“额度明细详情”，因为其对象与列表/详情层级不同；不是为了消除所有 mode。
- 奖励领取表单归领养；领取后的订单查看归投喂/履约读模型。订单种类必须保留，不能把奖励订单伪装成一条普通付费投喂 demo。

### 3.5 小院与动物

链路：**首页小院列表 → 小院详情 → 小院动物名册 → 动物详情；我的小院 → 管理动物 → 新增/编辑动物；创建小院 → 地址/位置 → 创建结果/管理入口 → 认证。**

- `commodityDetails` 更名为 `yard/detail`；此页是小院概况及动态/投喂摘要，不是商品详情。
- `yardCats` 拆成公开小院名册与管理名册。`roster/status/long-list` 是公开列表状态；`managed` 是管理任务。`publish-entry` 创建完成引导先归 onboarding 组件/QA，见矩阵，不以“无静态调用者”直接删除。
- `createCatYard` 更名 `yard/create`，`addKitten` 更名 `animal/editor`，`breedPicker` 更名 `animal/breed-picker`。猫狗通过 `species` 区分；可见产品文案按设计保留猫咪称呼，目录不把狗排除。
- `animal/detail` 是共用动物档案；领养、云养、投喂都是动作入口，不能改变动物身份。
- 相册归动物域，`animal/album` 保留独立管理权限。我的动物、我的云养、小院动物名册使用不同语义列表入口，复用 `PawPetRoster` 的表现，不混用所有权关系。

### 3.6 个人相关

链路：**我的 → 设置/地址/实名、个人资料、关注粉丝、等级勋章、历史；我的 → 领养/投喂/云养/小院等业务入口。**

- “我”是入口，不是所有业务的目录归属。`myAdoption` 移领养；`myFeedings` 移投喂；`myCloudPets` 移动物关系；`rescueProof*` 移救助。
- 用户主页和关注/粉丝归 `account`；主页内评价/动态等是用户聚合视图，不能把未接入的模板 tab 当成已实现页面。
- `myAssets` 的动物分支移出，勋章列表、勋章地图、勋章获得展示归个人成长；不同层级给明确路由，首次获得状态可复用勋章展示页。
- 地址和地区选择归 `address` 能力分包，登录/手机号/实名归 `auth`。不把所有通用能力塞进 `feature/common` 万能页面。
- “帮助过的动物”是个人贡献历史，保留 account 归属。助力页当前传入却未读取的 `id`，默认从调用方删除；未来真要显示某申请关联记录，需增加明确对象合同，不能默默解释成动物 ID。

### 3.7 投喂

链路：**小院/动物等入口 → 投喂操作弹层 → 结果；我的投喂/小院投喂订单 → 订单详情 → 反馈动态 → 返回订单；领养奖励领取 → 对应履约订单。**

- 本轮保持已批准的投喂弹层交互，不强行改成整屏结算页。复用 `YardFeedPopup`，逐步将其变成 props/emits 驱动的轻型交互，不携带所有订单 fixture。
- “我的投喂”和“小院投喂订单”是两个列表入口；它们分别关注个人支出/云养与小院履约责任。
- 同一订单详情保留 `perspective=donor|yard-manager` 显示意图，但实际能力由身份和订单关系派生。不能伪造 perspective 获得反馈权限。
- `feedingDetail90/91/92` 退出正式业务路由模型，按真实订单类型和字段形成页面状态；90/91 是角色/布局样例，92 的对象语义需要与奖励/云养读模型核对，不能仅凭数字合并或映射为支付成功。
- `postSuccess?state=feeding` 的投喂结果移到 `feeding/result`，与动态发布结果分离。
- 当前投喂订单和弹层存在 demo 行为。治理验收要求已有本地数据关系可回放；支付、生产投喂提交、正式上传发布不在本轮授权内。

### 4.2 分包规则的来源与适用

微信官方当前说明：整个小程序分包总大小不超过 30M，服务商代开发小程序不超过 20M，单个主包/分包不超过 2M。本方案把 1.5MiB 作为仓库质量门槛，不称其为微信强制限制。[微信分包加载](https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages.html)

Tab 页必须在主包；未落在分包 root 的产物归主包；普通分包不能同步 require 兄弟包 JS、引用兄弟包模板/私有资源。跨包导航到一个已注册页面与跨包 import 是不同操作。[微信使用分包](https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages/basic.html)

uni-app 支持分包内 static；其优化说明指出，仅被一个分包使用的 JS 可进入该包，被主包或多个分包使用的 JS 仍可能归主包。必须结合本项目锁定版本与最终产物验证，不能假设移源码就一定搬走依赖。[uni-app 分包配置](https://uniapp.dcloud.net.cn/collocation/pages.html#subpackages)、[uni-app 分包优化](https://uniapp.dcloud.net.cn/collocation/manifest.html#关于分包优化的说明)

本次微信官方页面通过直接 HTTP 读取核实；网页检索工具未能正常展开该域名。uni-app 路由文档仍显示 20M 的旧总量说明，平台额度采用微信官方口径。具体 AppID 是否属于代开发需接入发布验收时记录；本方案内部总量目标远低于两种额度。

### 4.3 允许与禁止的依赖

| 依赖 | 规则 |
|---|---|
| 分包页面 → 同包组件/服务/static | 允许，优先采用 |
| 分包 → 根基础组件、轻量 contracts/session/navigation | 允许，计入主包预算 |
| 主包页面 → 新分包页面 | 只用路由导航；禁止静态 import 页面/重型业务组件 |
| 分包 A → 分包 B | 路由跳转传业务 ID；禁止普通同步 import、模板和资源硬引用 |
| 全局 barrel 导出所有业务组件/fixtures | 禁止；容易把业务依赖重新带回主包 |
| 跨域共用同一单据 | 通过唯一服务合同及持久化记录，不通过复制 storage 模块/全局页面实例 |
| 独立分包、分包异步化 | 本轮不采用为默认架构；需专项验证初始化、占位、错误恢复和编译器支持 |

不要为了复用而新增“公共分包”让所有业务同步引用；这不符合普通分包引用规则。小型纯组件可以留主包；大型私有组合放所属分包；确有两个包需要的大模块，先拆职责/数据，再评估构建期受控复制或专项异步化，不能运行时直接引用兄弟包。

数据共享的具体落点：

- `services/contracts`、`services/session` 不导入 fixture 或页面；`SELF_PAW_ID` 与导航实现脱钩，mock 身份只由测试适配器注入。
- `applicationMockApi.ts` 拆成领养/救助域适配器；共享的响应形状和必要状态/存储边界可留根 `services`。禁止另造两份不一致的领养记录仓储。
- `jury` 大厅只取评审任务摘要，详情导航到业务分包；业务评审调用本域服务，并通过共享的轻量投票仓储维持同一 `reviewItemId` 的幂等结果。
- `rewardOrderId`、普通 `orderId`、`applicationId` 建立显式关联；feeding 与 adoption 读取同一订单合同。demo repository 可有不同 adapter，但不能让多个数组冒充同一订单。
- 保持现有 storage key 与数据，新增版本字段和一次性转换；未知/旧数据做容错，禁止以“清空缓存重测”代替迁移兼容。

### 5.6 首次进入分包与预加载

第一版使用普通分包，不开启 independent。从分享直达新分包时依然走统一应用初始化；会话读取和数据服务应提供可等待的初始化入口，不能假设用户已访问首页或“我的”。缺少记录与未登录分别处理，登录完成只恢复经过校验的目标。

先测“首页可交互时间、首次进入动态/小院详情、首次打开申请表、分包加载失败/重试”，建立缓存与无缓存两组数据；本方案不虚构当前延迟或承诺减小包体就一定更快。

预加载先采用小范围 Wi-Fi 策略，基于最终包体配置：首页优先 dynamic/yard 的高概率详情包；动物详情可在有明确领养意图后加载 adoption；个人中心不一次预下载所有个人业务。官方说明同一个分包各页共用 2M 预下载限额，规则必须合并计数，不按每页分别重置额度。预加载失败不影响当前页，真正点击仍可正常下载/重试；预下载不能解决主包超限或跨包非法 import。

对应 `preloadRule` 仅由 C0 在包稳定后配置，实际是否启用由冷启动测量与网络开销决定。规则来源：[微信分包预下载](https://developers.weixin.qq.com/miniprogram/dev/framework/subpackages/preload.html)。

## 6. 路由、参数、状态与旧入口兼容

### 6.1 合同

新建轻量 `navigation`，提供 `buildRoute(name, params)`、`navigate(name, params, method)`、`parseRouteQuery(name, query)`、`resolveLegacyRoute(path, query)` 和返回目标白名单。名称表只含字符串/小型校验元数据，禁止 import 页面、业务服务和 fixture。

`pages.tson` 仍是 uni-app 编译页面注册源；目标路由表、`figma-map` 与其有自动一致性检查。矩阵是迁移设计，不能长期成为另一个无人同步的运行时真源。第一阶段不必引入代码生成框架，更不必为此迁全仓 TypeScript；JS + JSDoc 即可。

| 目标参数 | 用途 | 旧别名的处理 |
|---|---|---|
| dynamicId | 动态身份 | 仅 yardId 的旧链接不能伪造为某条动态；展示关联小院/找回入口或明确历史不可恢复 |
| yardId | 小院身份 | 小院详情旧 `id` 只在 legacy adapter 转换 |
| animalId | 动物身份 | 对应页面的 `petId/id` 转换；不在全局把所有 id 当 animalId |
| applicationId | 领养申请身份 | 领养语境下 `recordId/id` 转换 |
| rescueId | 救助申请身份 | 救助语境下 `id/recordId` 转换 |
| orderId | 投喂/履约订单身份 | `id` 只在明确旧订单路由转换；奖励单还需关联 applicationId |
| reviewItemId | 投票任务身份 | `itemId/id` 转换；不是申请 ID，需查任务获得关联业务 ID |
| userId | 用户身份 | profile/关系页 `pawId/userPawId` 经适配映射为当前逢猫号；不宣称已是后端 UID |
| species | cat/dog | animal/yard 表单中的 `kind/type` 转换 |
| kind / intent | shipping/service、manage/select | 地址列表/表单的有限枚举 |
| view / filter / outcome | 页内子视图、筛选、同域结果 | 将 frame/mode/variant 对照显式表转换 |

页面可选 `origin` 作为有限来源枚举，例如 `yard|animal|me|share`；不接受任意函数、任意 URL、整条单据、地址/手机号作为导航参数。显示角色、`managed=1`、`reviewerId` 不产生操作权限。

### 6.2 生产状态与 QA 状态分离

- 业务状态由服务读取，URL 只定位记录/只读视图，不能 `frame=57` 就推进为奖励成功。
- QA 画板号保留在设计映射/fixture 索引，转为命名 fixture，如 `adoption.owner-pending`。仅开发/测试构建允许加载，生产构建剔除 override 和测试状态修改入口。
- 禁止由结果页 onLoad、旧路由适配、默认 query 产生业务写入。
- `state=long` 的救助语义已由正文和 Figma 确认：旧链接仅在无冲突救助/动物上下文时规范到救助申请；若同时明确 `source=adoption` 或携带已存在的领养单，则拒绝冲突输入，不能自动改写成另一业务。
- 缺 ID、记录不存在、无权访问、任务类型与链接不符，均有可返回空态；不使用“第一条记录/最后一条记录”兜底生产路由。

### 6.3 兼容路由不是 Vue Router alias

微信小程序旧 URL 要继续可达，必须继续在 `pages.tson` 注册对应旧页，并存在实际轻量页面文件。中央 resolver 不能挽救根本未注册的旧路径。

旧路径可保持字符串不变而调整注册包归属。例如消息列表迁出后，将 `/pages/messageDetail/index` 的兼容壳注册到 root=`pages/messageDetail` 的小型兼容分包，主包仍可只有四个 Tab 业务页。不要把所有旧壳迁到一个新 legacy 路径后声称旧 URL 已兼容；旧 root 的开销计入迁移预算。

迁移一个页面的原子步骤：

1. 建新目标页和合同测试，保留同一业务数据/状态。
2. 旧路径变成仅解析参数并 `redirectTo` 的壳；目标是 Tab 时用 `switchTab`。壳不 import 新分包页面，不持有业务组件/资源。
3. 更新所有内部调用方、分享卡片、消息落地目标、返回 fallback、QA 示例、设计索引。
4. 验证旧/新深链、冷启动、页面栈、空参数、错误 ID；确认兼容壳不循环、不会重复提交。
5. 包报告检查老页面重型依赖已真正消失，新增壳成本入账。

路径前后案例：

```text
/pages/feature/index?mode=rescue-detail&rescueId=R1
→ /packages/rescue/pages/detail/index?rescueId=R1

/pages/meMore/adoptionFlow?type=rescue&rescueId=R1
→ /packages/rescue/pages/progress/index?rescueId=R1

/pages/meMore/adoptionFlow?id=A1&frame=48
→ /packages/adoption/pages/progress/index?applicationId=A1&view=adoption-info

/pages/yard/juryDetail?reviewType=rescue&itemId=J1
→ /packages/rescue/pages/review/detail/index?reviewItemId=J1
```

本次已核对 `PawAdoptionFlowFigma`：48 标题是“领养信息”，展示小院位置和联系方式；49 是“申请内容”。C0 按这个映射冻结合同和测试，其他编号也必须读内容，不能凭编号次序推断。

无 type 的旧 `juryDetail` 应先按 `reviewItemId` 查询共享轻量任务元数据，再跳目标域；查不到给空态。不能默认 rescue 或 adoption。旧 `juryPanel` 保留到统一任务大厅的跳转，`businessType` 只是筛选条件。

生产旧分享链接不设机械两周删除期。建议至少跨两个已发布版本保留，采集旧入口命中后评估；对外分享/二维码可能长期有效，应继续保留轻量壳，除非有明确失效策略。仅 QA 入口在确认无外部使用后从生产配置剔除。旧 root 中一旦删掉最后一个注册页，必须同步移除 root 和残留输出，避免被重新算入主包。

若 90/91/92 等数字路径因历史链接仍需生产注册，应标记为 `legacy`，只能解析真实对象或显示不可恢复提示；自动生成 demo/切换画板状态的实现仍只存在 dev。保留旧 URL 与发布 QA 页面是不同的验收项。

### 6.4 返回、选择器和生命周期

- 列表→详情使用 `navigateTo`；成功替代提交页、旧壳跳新页使用 `redirectTo`；`reLaunch` 仅明确重置栈，避免吞掉上游流程。
- 回 Tab 不拼 query；使用 `switchTab`，必要筛选通过经过验证的轻量状态/持久化恢复。
- 地址/品种/动物选择保留 `eventChannel`：`requestId` + 选择输入 + 选择结果事件；取消不提交。冷启动没有 opener 时提供正常管理模式或明确返回入口。
- **不能简单用 redirect 迁选择器**：原 opener 的 eventChannel 不会自动传给新的页面。优先先迁调用方直达新选择器；仍需兼容的旧包装页承担有期限的事件转发并测试，或用 requestId 临时结果通道恢复。不得整仓替换 URL 后才发现回填丢失。
- `returnUrl` 替换为白名单 returnTarget + 有限参数；旧值解析失败时返回安全的列表/Tab，不执行任意深链。
- `onShow` 重新按 ID 读取变更，恢复筛选/滚动/选中状态；禁止无条件重置首页、编辑草稿和返回后的上下文。

布局整改按原审计区分风险：核心结构依赖绝对坐标的首页、排行榜、用户主页、小院/动物编辑等优先改正常文档流；固定底栏、弹层、徽标、局部覆盖是允许的布局手段，不做“全仓去 absolute”或 rpx→px 机械替换。

导航/安全区更改前读取 `docs/AGENTS-native-ui-rules.md` 与 `docs/pages-design/PawPageNav.md`：`PawPageNav` 固定定位且提供等于运行时导航高度的占位；业务间距归页；原生胶囊只透明避让；不绘制状态栏、胶囊、Home Indicator。照片保持比例；Icon/字/线/圆角/触摸区用 px；viewport 相对留白才考虑 rpx。

语义迁移与大规模视觉重排拆成不同 PR。每轮 1–3 个相关 UI 问题→构建→运行时→几何/截图，连续两次无改善先排查组件、继承、单位、安全区、缓存，不叠加覆盖 CSS。

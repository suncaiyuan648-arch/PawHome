## Data boundary

`create/get/update/advance/listApplications` now reject an unknown application type with `INVALID_TYPE` before touching either storage domain. Rescue writes stay on `PAWHOME_RESCUES`; adoption writes stay on `PAWHOME_ADOPTIONS`. A type is never inferred from an ID, role, or query field.

Reward persistence has one source, `PAWHOME_REWARD_ORDERS`. `rewardOrderStorage.ts` is a lightweight ESM storage seam with no fixture or photos dependency. New orders carry both `applicationId` and legacy-compatible `recordId` with the same value. Existing orders that only carry `recordId` are read through the same association helper and are returned with the explicit `applicationId` alias; mismatched association fields are not merged.

`createRewardOrder` reads a saved adoption record with `includeDemo: false` and accepts only `adoption_confirmed`, `reward`, or `reward_done`. Missing applications, rescue IDs, early stages, and `reward_done` without an existing associated order fail without creating an order. An existing order for the same application is returned idempotently, including the intermediate state where the order was saved but the application transition later failed. `address.id` remains required as in the existing caller contract. Exact order lookup has no demo or first/last-record fallback.

Storage write exceptions are converted to structured `STORAGE_WRITE_FAILED` responses. A failed order save does not advance or alter the adoption record; a failed application transition remains a failed transition. This is still a local mock boundary: it does not provide backend existence, authentication, address authorization, payment, delivery, or final reward completion proof. A result page must verify order/application state from the corresponding record; query parameters do not prove completion.

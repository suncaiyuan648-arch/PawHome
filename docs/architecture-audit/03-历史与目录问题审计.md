## 4. 目录语义与路由职责候选

### 4.1 pages/yard/yardCats.vue 同时包含小院成员列表与遗留 publish-entry 页面分支

- 事实证据：pages.json:456-481 将该路由放在“**小院管理分包**”，配置路径是 pages/yard/yardCats。当前文件的 roster/status/managed 分支渲染 PawPetRoster（pages/yard/yardCats.vue:8-12），而 publish-entry 分支改为自有导航、显示“**小院猫咪**”（pages/yard/yardCats.vue:14-27），底部操作是“**完成创建**”（pages/yard/yardCats.vue:67-69），并打开“小院创建完成/前往认证”弹层（pages/yard/yardCats.vue:118-126）。onLoad 明确接受四个不同的 state（pages/yard/yardCats.vue:210-216）。
- 导航事实：当前可检索到的页面调用者把此路由用于 state=roster（pages/dynamicDetail/index.vue:251-254、pages/commodityDetails/index.vue:81-85）和 state=managed（pages/me/index.vue:404-406）。在 pages/、components/、utils/ 中没有检索到 state=publish-entry 调用者；因此不能仅凭变量名断言当前线上入口确实是“发布动态”。
- 判断级别：**高概率**存在职责漂移或遗留分支；“发布动态是否曾经使用该状态”本身为**待确认**。当前真实发布动态路由反而是 pages/publishDynamic/postFeed：pages.json:321-344、docs/design/figma-map.yaml:83-97、components/CustomTabber/index.vue:78-80 和 pages/publishDynamic/postFeed.vue:6-17 均相互印证。
- 影响：小院成员管理、创建完成后的认证引导和可能的发布前选宠物职责共存；删除或修改列表逻辑时可能误伤不可见深链，新增状态也会继续扩大单页条件分支。
- 后续重构建议：先从外部分享/历史深链确认 publish-entry 是否仍需保留；若无调用，删除该状态前补一次路由回归；若仍需选宠物/创建后的过渡，拆成明确的 pages/yard/yardPetPicker 或 pages/publishDynamic/selectPets（以产品语义为准），保留 PawPetRoster 等组件复用。

### 4.2 救助评审列表位于 pages/yard，但当前分包语义是“小院管理”

- 事实证据：pages.json:456-529 把 rescueReview 注册在“**小院管理分包**”；页面文件本身只是包装器（pages/yard/rescueReview.vue:1-10），实际组件标题是“**救助评审**”，内容是救助基金余额/统计/状态列表（components/PawRescueReviewPage.vue:3-40），卡片字段是求助金额、救助说明和浏览数（components/PawRescueReviewPage.vue:40-60），跳转到救助详情而不是小院详情（components/PawRescueReviewPage.vue:135-140）。
- 反证与限制：docs/design/figma-map.yaml:188-220 明确把 rescue 业务的入口/source 也记录为当前 pages/yard/rescueReview.vue，docs/pages-design/领养流程全链路任务清单.md:82-87 也把它作为救助链路入口。因此“放错目录”不是已证实缺陷，而是目录按“管理/评审”而非按“救助”分域的设计选择。
- 判断级别：**待确认**。
- 影响：未来增加救助申请人视图、管理员视图或救助详情时，yard 分包名会误导路由检索、权限边界和模块归属；当前功能不会因目录名自动失效。
- 后续重构建议：先确定顶层域是 yard（院主/管理能力）还是 rescue（救助业务）；若按业务域拆分，迁移到 pages/rescue/review 并保留旧路径兼容跳转，组件包装器可继续保留；若按角色聚合，至少把分包/路由注释从“小院管理”改成包含救助评审的管理域，并在路由契约中声明权限角色。

### 4.3 pages/adoption/adoptApply.vue 用 state/source 同时承载领养申请与救助申请

- 事实证据：pages.json:394-419 将 adoptApply 注册在“领养业务分包”。文件标题却根据 longMode 在“**求助申请**”和“**领养申请**”间切换（pages/adoption/adoptApply.vue:1-5）；表单卡片和宠物区也分别显示“申请救助的动物/申请领养的猫咪”（pages/adoption/adoptApply.vue:30-35）。onLoad 用 state=long 与 source=rescue 进入救助模式（pages/adoption/adoptApply.vue:145-150），提交分支会调用 createApplication('rescue', ...) 并带 type=rescue&rescueId 跳转（pages/adoption/adoptApply.vue:312-353），普通分支则调用 createApplication('adoption', ...) 并带 recordId 跳转（pages/adoption/adoptApply.vue:355-389）。发布抽屉的“救助”入口直接导航到 adoptApply?state=long&source=rescue（components/CustomTabber/index.vue:86-89）。
- 判断级别：**高概率**是目录与实际业务域不一致，同时也是一个通过查询参数承载两个业务表单的路由复用候选；表单骨架复用本身是合理的，不能据此断言实现错误。
- 影响：领养和救助会共享标题、校验、媒体、宠物选择与提交边界；后续救助权限、金额、实名/协议和状态机变化可能把领养分支带入回归，路由分析也会漏统计救助入口。
- 后续重构建议：保留共享表单组件和媒体/宠物选择组件，新增明确的 pages/rescue/apply.vue 与 pages/adoption/adoptApply.vue 页面壳；把 applicationType 作为显式契约传给共享逻辑，分别接入 rescue/adoption storage/API，并对旧 adoptApply?state=long&source=rescue 做兼容重定向。

### 4.4 pages/adoption/adoptApplySuccess.vue 用 type=rescue 承载救助申请成功页

- 事实证据：pages.json:394-428 把该页面注册在领养业务分包，并在配置注释中描述为“领养申请提交成功”。源码却根据 type/source/sourceType 切换 applicationType（pages/adoption/adoptApplySuccess.vue:28-39），标题、正文和按钮在救助类型下分别为“**救助申请成功**”“查看救助进度”，领养类型下为领养文案（pages/adoption/adoptApplySuccess.vue:52-60）。上一个候选的救助提交分支明确跳到 type=rescue（pages/adoption/adoptApply.vue:344-352）。
- 判断级别：**高概率**存在路径语义不一致；同一个结果页壳复用并不等于业务必须共用路由。
- 影响：路由统计、权限/埋点和救助链路导航会落入 adoption 目录；救助结果状态扩展容易污染领养成功页。
- 后续重构建议：选择 pages/rescue/applySuccess.vue 与 pages/adoption/adoptApplySuccess.vue 两个入口，共享 PawFlowResult/结果展示组件；旧 query 继续兼容一段时间，并在统一导航工具中集中完成类型到路由的映射。

### 4.5 pages/meMore/adoptionFlow.vue 用 type/source 同时承载领养进度与救助进度

- 事实证据：pages.json:175-185 的注释是“领养流程”；模板却根据 applicationType 在 PawApplicantRescueFlow 和 PawAdoptionFlowFigma 之间二选一（pages/meMore/adoptionFlow.vue:1-4）。onLoad 读取 type/source/sourceType（pages/meMore/adoptionFlow.vue:12-18），adoptApplySuccess.vue:47-49 会对救助类型生成 /pages/meMore/adoptionFlow?type=rescue&rescueId=...。仓库设计记录也明确写出“领养单和救助单共用 /pages/meMore/adoptionFlow 路由，由 type/source 区分”（docs/pages-design/领养流程全链路任务清单.md:101-110）。
- 判断级别：**确认**存在跨业务类型路由复用；是否现在就拆分为**待确认**，因为设计文档明确把它作为普通申请者侧的统一进度入口。
- 影响：同一路径下存在不同 ID 名称（recordId/领养 ID 与 rescueId）、不同状态来源和不同展示组件；路由守卫、返回路径和埋点若只按 adoptionFlow 判断会发生边界遗漏。
- 后续重构建议：短期保留现有兼容入口，但把 query 解析收敛为显式 applicationType 枚举和统一 ID 合同；中期提供 pages/adoption/progress.vue、pages/rescue/progress.vue 两个薄壳，共享状态卡片和进度组件，旧路径只做兼容转发。

### 4.6 pages/feature/index.vue 用 mode 承载救助详情、邀请入驻、宠物相册

- 事实证据：pages.json:243-253 只注册了一个“通用功能场景页”。模板的三个互斥分支分别是救助详情（pages/feature/index.vue:5-110）、邀请入驻（pages/feature/index.vue:112-134）和宠物相册（pages/feature/index.vue:135-166）；onLoad 用 mode=rescue-detail/invite/album 选择分支，album 还要求 managed=1（pages/feature/index.vue:374-393）。实际调用者分别来自救助评审/证实、我的页面邀请和宠物详情相册：components/PawRescueReviewPage.vue:135-140、pages/me/index.vue:376-378、pages/adoption/petDetail.vue:300-304。
- 判断级别：**确认**是一个路由文件承载三个不相干的页面上下文；“feature”虽是泛化目录，但不能消除模板、权限和导航职责已经分叉的事实。
- 影响：救助投票/评论、入驻邀请、受权限控制的相册共享同一生命周期与页面样式；任一模式改动都增加无关回归面，页面级权限和分享配置也难以独立。
- 后续重构建议：拆为救助详情、邀请入驻、宠物相册三个显式页面入口，分别保留 rescueId、邀请上下文和 managed/petId/yardId 契约；评论、相册菜单、分享弹层等继续下沉为组件，旧 feature/index?mode=... 仅保留兼容转发。

### 4.7 pages/messageDetail/index.vue 用 type 承载服务、互动、活动三种页面

- 事实证据：pages.json:18-31 将其描述为“查看单条消息或指定消息类型”；源码模板按 type=service/interaction/activity 渲染三个完全不同的顶层结构（pages/messageDetail/index.vue:5-34），标题也分别为服务订单消息、互动消息、活动消息（pages/messageDetail/index.vue:64-68）。消息中心确实按消息行类型导航到该路由（pages/message/index.vue:148-152）。
- 判断级别：**确认**存在多类型路由复用；是否拆分为三个真实路由为**待确认**，因为三者仍属于消息中心同一产品域，messageDetail 是有意义的聚合命名。
- 影响：服务订单、社交互动和官方活动的详情数据合同与交互完全不同；继续扩展其中一种类型会把条件分支和消息详情组件变成“万能页”。
- 后续重构建议：先建立 messageType -> handler/component/route 注册表，统一参数校验；当任一类型需要独立权限、分享或数据加载时，再拆为 serviceMessage、interactionMessage、activityMessage 薄壳并保留旧路由兼容。

### 4.8 pages/adoption/extras.vue 用 mode 承载助力领养、领养额度、额度明细

- 事实证据：pages.json:394-435 已注明“领养扩展场景，通过 mode 参数承载支持、名额等补充页面”。源码标题按 support/quota/quota-detail 变化（pages/adoption/extras.vue:55-72），模板内容从“助力领养”支持列表切换到额度、交易明细与退款说明（pages/adoption/extras.vue:1-47）；我的页从不同入口传入 mode=quota、mode=support（pages/me/index.vue:364-366、pages/me/index.vue:407-409）。
- 判断级别：**待确认**。三者都在领养额度/助力同一业务域内，当前更像有限状态页复用，不足以单独判为不相干路由。
- 影响：额度账本、助力列表和明细数据会在同一页面中累积条件分支；但拆分收益目前低于统一状态入口的成本。
- 后续重构建议：先将三个模式抽成独立内容组件并用类型化模式表注册；只有当数据加载、权限或分享规则分叉时，再拆成 adoption/support、adoption/quota、adoption/quotaDetail。

### 4.9 pages/meMore/myAssets.vue 用 mode 承载宠物资产、勋章、勋章地图和新勋章

- 事实证据：pages.json:198-212 将其描述为“我的资产”；模板包含宠物列表、勋章页、勋章地图和新勋章四个大分支（pages/meMore/myAssets.vue:1-120），onLoad 根据 mode 读取 pets/medals/map/new（pages/meMore/myAssets.vue:128-145），并在分支间以带 mode 的同一路径跳转（pages/meMore/myAssets.vue:157-186）。
- 判断级别：**待确认**。宠物与勋章是不同的资产子域，但“我的资产”可以是有意聚合入口；仅从目录/文件名不能推断为错误。
- 影响：宠物管理与勋章视觉/数据状态共享页面生命周期；新增资产种类会继续扩大 mode 的枚举和回退行为。
- 后续重构建议：保留“我的资产”入口，先把宠物、勋章、地图、新勋章拆成内容组件与显式状态契约；若产品导航把它们作为独立页面，再迁移为 myPets、myMedals、medalMap、medalDetail，并保留旧 query 兼容。

## 5. 有意复用但本轮不判为“不相干”的对照项

- pages/yard/juryPanel.vue 与 pages/yard/juryDetail.vue 都接受 reviewType=rescue/adoption（pages/yard/juryPanel.vue:58-102、pages/yard/juryDetail.vue:130-142、pages/yard/juryDetail.vue:217-225），但两者仍是同一“评审团列表/详情”交互模型，只是评审对象类型不同。
- pages/yard/adoptionAudit.vue 的 list/info/application/ownerReview/cloudReview/ownerConfirm/... 是同一领养审核状态机（pages/yard/adoptionAudit.vue:178-215、pages/yard/adoptionAudit.vue:256-297），不是若干独立业务页面的偶然拼接。
- pages/adoption/result.vue 的 variant=80-85 都是领养流程结果状态，并且统一通过 routes 进入进度/审核链（pages/adoption/result.vue:96-125）；pages/meMore/feedingDetail.vue 的 type=yard-owner/cloud-parent 也是同一投喂订单详情的角色视角（pages/meMore/feedingDetail.vue:1-5、pages/meMore/feedingDetail.vue:120-178）。
- pages/publishDynamic/postFeed.vue 的 state=alternate 仍是发布动态的同一表单/反馈上下文（pages/publishDynamic/postFeed.vue:11-17、pages/publishDynamic/postFeed.vue:161-179），不能与“发布动态和发布救助单共用同一路由”混为一谈。

## 6. 审计结论与实施顺序

1. 优先确认并处理 pages/adoption/adoptApply.vue、adoptApplySuccess.vue、meMore/adoptionFlow.vue 的 adoption/rescue 路由契约；它们已经有明确的 type/source/rescueId 证据，是影响权限、状态机和埋点的最高价值候选。
2. 再处理 pages/feature/index.vue 的三模式分叉，以及 pages/yard/yardCats.vue 中没有当前调用者的 publish-entry 分支。
3. 对 rescueReview、messageDetail、extras、myAssets 保留产品/权限确认，不应只凭目录名机械迁移。
4. 迁移期间保留旧路由兼容，先建立参数枚举、ID 合同和统一导航映射，再删除旧入口；共享组件继续复用，避免通过复制页面实现“目录变清晰”。

本次只读审计未修改业务源码；实际落盘文件仅为本报告 docs/architecture-audit/03-历史与目录问题审计.md。覆盖范围为当前 HEAD 下全部 63 个页面入口、全部 107 个组件文件，以及 pages.json 的全部 63 个路由注册项。

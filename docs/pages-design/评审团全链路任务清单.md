## 1. 审计结论

初始审计确认列表筛选、统一数据、投票状态机、结果弹窗、下一条路由和 Figma 映射均未完整打通；本轮已完成 P0/P1 实现和视觉 review：

- 列表的“待投票/投票结束”由 `juryStorage` 投影后的 item 状态筛选，计数随本地投票更新。
- 评审 item、申请人、院主、宠物、证据、申请材料和奖励均通过稳定 item/application/record ID 关联。
- 默认链路可直接投票；投票结果按 real/fake 使用 `PawDialog`，返回、关闭和“好的”均保持 item 状态。
- 已投票详情支持按当前待投票队列进入下一条，队列耗尽后返回评审团；列表和详情均使用 `PawPageNav`，不重绘原生 UI。
- 评审团页面、详情页和结果弹窗的 Figma 节点已登记在 `docs/design/figma-map.yaml`；图片使用仓库内 Figma 源素材，未引入切图或临时远程 URL。

当前仍未接入生产评审 API；本轮验收范围是本地 mock + 本地持久化状态机，生产接口前置项见第 5 节。

## 3. 实施任务

### P0：统一数据与可重复状态机

- [x] `JURY-001` 建立统一评审 mock 数据源：评审 item、申请人、院主、申请宠物、证据图片、投票比例、投票结束状态、奖励信息均使用稳定 `id`。
- [x] `JURY-002` 建立评审状态仓储：读取/保存/清除本地 vote，按 item ID 判断待投票或已投票，支持刷新和重复进入不丢状态。
- [x] `JURY-003` 修复正常投票链路：移除永久 demo 拦截；保留“今日投票次数用完”作为可控 mock 场景，不阻断默认主链路；首次点击 real/fake 后保存并打开对应结果。
- [x] `JURY-004` 打通列表 → 详情 → 投票结果 → 列表/下一条：结果关闭回到已投票详情，下一条按当前筛选列表顺序进入下一项，最后一条给出完成态并可回列表。
- [x] `JURY-005` 列表筛选与计数由仓储派生，待投票和投票结束在同一数据源上更新；入口返回和页面重进保持当前状态。

## 4. 验收约束

- 默认 mock 必须能从入口直接完成一次投票，不依赖手动修改代码或 storage。
- 投票结果必须以 item ID 关联，不能使用全局单一 `voted` 布尔值代替。
- 列表和详情刷新后仍能识别已投票项；下一条不能重复打开当前 item。
- 任何 Figma 设备壳、系统状态栏、胶囊和 Home Indicator 仅作为设计参考，不进入小程序业务页面。
- 全链路测试必须在所有实现、静态检查和视觉 review 完成后执行，之前只允许做必要的构建/静态诊断。
